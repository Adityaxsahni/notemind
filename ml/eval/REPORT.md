# NoteMind evaluation report

How well NoteMind finds the right pages in a student's notes, and how good its answers are.
Tables between `BEGIN`/`END` markers are generated by `python -m ml.eval.run`; the analysis
around them is written by hand after each run.

## Method

**Question sets.** `ml/eval/data/<set>/questions.jsonl`. Each question has gold
`(document, page)` labels and a reference answer:

- **single**: one page answers it (several acceptable pages may be listed)
- **multi_hop**: needs every listed page
- **unanswerable**: on-topic but not covered by the notes; the right response is
  "I couldn't find this in your notes"

**Seed set (this report).** Three short synthetic courses written for this evaluation:
DBMS (PDF, 8 pages), Operating Systems (PPTX, 10 slides with speaker notes) and Machine
Learning (DOCX, 7 sections). 87 hand-labelled questions: 64 single, 7 multi-hop,
16 unanswerable. The text is clean and the questions were written by someone who knew it,
so **absolute numbers are optimistic**; the set is for comparing configurations and as a
CI regression gate. Headline numbers need the real-notes set (see "Next steps").

**Pipeline under test.** The app's own code: extraction → cleaning → heading-aware
chunking → `bge-small-en-v1.5` embeddings → pgvector HNSW + Postgres full-text → RRF →
cross-encoder rerank → top 6. Each course is its own collection, as in the app;
"combined" variants put all three courses in one collection (three times the distractors).

**Retrieval metrics** (page level; several chunks of one page count once):
Recall@k (single: any gold page in the top k; multi-hop: share of gold pages in the top k),
MRR, nDCG@6. **Refusal**: a question is flagged "not in your notes" when the best reranker
score is below the cutoff (`RETRIEVAL_MIN_SCORE`, default −6.0). Refusal recall = share of
unanswerable questions flagged; false refusal = share of answerable questions flagged.
Latency = query embedding + both searches + rerank, on a laptop CPU (no GPU).

**Answer metrics** (LLM judge with a fixed rubric, `ml/eval/judge.py`): correctness against
the reference answer (1 / 0.5 / 0), faithfulness (share of the answer's claims supported by
the retrieved sources), citation precision (cited pages that are gold pages), refusal
behaviour, time to first token, and cost per question at list prices. The judge is trusted
only after its agreement with human labels on 40 sampled answers is measured
(`run.py label` / `run.py agreement`).

**Reading the table.** Recall@6 is saturated: the right page reaches the top 6 for every
answerable question in almost every variant, because the seed set is small and clean. The
variants differ in **ranking** (R@1, MRR) and in **refusal**, so those columns drive the
decisions below.

- **The reranker earns its 0.3 s.** It lifts MRR from 0.97 (hybrid without rerank) to 0.99,
  and from 0.91 for vector-only. It also provides the confidence score used for refusal.
  Search without reranking has no calibrated score, so it can't say "not in your notes".
- **Hybrid beats either search alone.** Keyword-only (MRR 0.95) beats vector-only (0.91)
  here because students ask with the notes' own terms. In the combined collection, which has
  three times the distractors, vector-only is the only variant to lose recall (R@6 0.96).
  Hybrid without reranking stays at 1.00, so keyword search is what keeps recall up as
  collections grow. Behind the reranker the difference vanishes: vector → rerank equals
  hybrid → rerank on this set.
- **Chunk size barely moves retrieval; 200/30 is the best on every column.** It's the only
  variant with MRR 1.00 apart from bge-base. 800/120 exceeds the embedder's 512-token window,
  so chunk tails are never embedded; it didn't hurt on these short pages but would on dense
  real notes. Overlap (60 vs 0) made no measurable difference.
- **Pool size: 10 is enough here.** Reranking 10 candidates per method matches 30 on every
  metric and cuts combined-collection latency from 1.45 s to 0.50 s, because rerank cost
  grows with the pool. (The single-collection latencies of 0.3–0.6 s are within run-to-run
  noise on a laptop CPU.)
- **`bge-reranker-base` isn't worth it.** Its ranking is the same as MiniLM's (MRR 1.00 vs
  0.99), but p50 latency is 14× higher (4.4 s). Its scores are on a different scale, so the
  −6.0 cutoff catches only 38% of unanswerable questions; switching rerankers means
  recalibrating the cutoff.

### Confidence cutoff

Best cutoff on this set, per reranker (maximising balanced accuracy between refusing
unanswerable questions and answering answerable ones):

"Best" weighs both errors equally, but they don't cost the same. A **false refusal** tells
the student their notes don't cover something they do; nothing downstream can fix that. A
**missed refusal** only sends the question to the LLM, which is instructed to say when the
sources don't answer it. The cutoff is a cheap first gate, not the only defence, so it
should sit below the balanced optimum. A sweep of the cutoff on the baseline and on 200/30
chunks (16 unanswerable, 71 answerable questions):

| Cutoff | 400/60: refusal recall | 400/60: false refusal | 200/30: refusal recall | 200/30: false refusal |
|---|---|---|---|---|
| −8.0 | 0.56 | 0.00 | 0.50 | 0.00 |
| **−6.0** (current) | 0.75 | 0.03 (2 q) | 0.69 | 0.01 (1 q) |
| −5.0 | 0.75 | 0.04 (3 q) | 0.81 | 0.01 (1 q) |
| −4.0 | 0.88 | 0.08 (6 q) | 0.88 | 0.03 (2 q) |
| −2.4 | 0.94 | 0.11 (8 q) | 0.94 | 0.03 (2 q) |

Smaller chunks separate the two groups far better. With 400/60 chunks, six answerable
questions score between −7.9 and −3.6, because the answer is one sentence diluted by a
chunk about something else. With 200/30 chunks only two do. Two kinds of question get past
any cutoff:

- `os-13` "When are spinlocks a good choice?" is answerable but scores −7.9 at both sizes.
  The slide says *when* without the word "good", so this is a recall problem for the
  reranker, not the cutoff.
- `dbms-30` "two-phase commit" (+0.6 / +3.5) and `os-25` "monitors" (−2.7) are
  unanswerable but sit next to covered material (two-phase *locking*, semaphores). Only the
  LLM's own refusal can catch these, which is what the answer evaluation measures.

## Recommended configuration

| Setting | Current default | Recommended | Evidence |
|---|---|---|---|
| Search | hybrid (vector + keyword, RRF) | **keep** | Only setup that keeps R@6 = 1.00 in the combined collection without reranking |
| Reranker | MiniLM-L6 | **keep** | Same ranking as bge-base at 1/14 of the latency |
| Top k sent to the LLM | 6 | **keep** | R@6 = 1.00 everywhere; multi-hop questions need room for two pages |
| Chunks (`CHUNK_TARGET_TOKENS`/`CHUNK_OVERLAP_TOKENS`) | 400/60 | **200/30**, after the real-notes check | Best MRR (1.00); false refusal falls from 3% to 1% at the same cutoff |
| Cutoff (`RETRIEVAL_MIN_SCORE`) | −6.0 | **−5.0** together with 200/30 chunks; keep −6.0 with 400/60 | Refusal recall 0.81 at 1% false refusal (table above) |
| Rerank pool (`RETRIEVAL_CANDIDATES`) | 30 | **keep for now**; 10 if latency matters | No quality loss at 10 on this set, and a third of the latency on large collections. Real notes are messier, so confirm first |

The chunk-size change is deferred because the seed set can't settle it alone: 16
unanswerable questions is a small sample, and the improvement comes from 4 questions.
Changing chunk size also means re-ingesting every existing document. If the real-notes set
shows the same pattern, switch both chunk size and cutoff in one release.

## Next steps

1. **Real-notes set.** 150 questions over 3 real courses, 20% unanswerable and 10% multi-hop.
   Draft them with `run.py generate`, review each one by hand, then re-run this report.
2. **Answer evaluation.** Needs an LLM key. Run on 5 questions (`--limit 5`) first, then the
   full set, then label 40 answers (`run.py label`) and report the judge's agreement with the
   human labels (Cohen's κ).
3. **Re-decide chunk size and cutoff** on the real set, using the sweep above.

## Reproduce

```bash
uv run --project backend --group eval python -m ml.eval.run retrieval --set seed
uv run --project backend python -m ml.eval.run answers --set seed --yes
uvx --from mlflow mlflow ui --backend-store-uri sqlite:///ml/mlflow.db   # browse runs
```
